# Local Viya JS twin mock

For a trusted, disposable desktop, enable Viya emulation, run with the JS runtime, and set the existing `LOCAL_VIYA_JS_JOBS` JSON map, for example `{"/app/job":"/app/job.js"}`. The named Drive JS file is executable trusted code. With a definition-capable API, a deployed definition with the same folder and name is listed once and returned unchanged. The adapter's web executor sends `__program` and `_job` to the Server's emulated `/SASJobExecution/` tier: the Server middleware resolves the `_job` definition URI to a registered JS twin. `__program` is an ordinary pass-through variable, not a selector or control. Compute matches its submitted code after the adapter's CRLF normalization (including empty persisted code); JES matches the definition ID and selector. Only the registered JS twin runs: the definition's SAS is not interpreted. Unknown selectors, mismatched code or absent JS files fail. Debug logs identify JS mock execution.

When this mock registry is enabled in desktop mode, definition creation is enabled for a private, disposable Drive with no concurrent writers; definition discovery, matching and creation are not transactional. It is not a multi-user or production safety boundary. Folder, file, tree and execute authorization remain in force. JS twin behavior is a separately authored simulation and is not evidence of SAS execution or equivalence.

The Compute JS reader requires Linux procfs. If static script mocks are also configured, those take precedence over JS twins. Existing synthetic-token discovery remains available when no definition is deployed. Normal non-mock SAS-enabled server behavior is unchanged.
